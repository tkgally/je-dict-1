## Implementation Steps

### Part A: Extend review_runner.py with Two-Pass Pipeline

Read `build/review_runner.py` (created in prompt 12) and add:

#### Pass 1 — Screening
Add a `--pass screening` mode:
1. Uses a cheap model (Gemini Flash or GPT-4.1-mini via OpenRouter)
2. Processes entries in bulk (higher throughput, lower cost)
3. For each entry, sends a lightweight prompt that asks: "Are there any potential furigana reading errors in this entry?"
4. Stores screening results in `reviews/screening/{entry_id}.json`:
   ```json
   {
     "entry_id": "12345",
     "screened_at": "2026-04-09T...",
     "model": "gemini-2.5-flash",
     "flagged": true,
     "concerns": ["Potential misreading in example 3"],
     "confidence": 0.7
   }
   ```
5. Supports `--range START END` for processing ID ranges
6. Tracks screening coverage in `reviews/screening_status.json`

#### Pass 2 — Deep Review
Add a `--pass deep` mode:
1. Processes only entries flagged in screening (or entries specified with `--ids`)
2. Sends to multiple strong models (GPT-4.1 + Gemini 2.5 Pro)
3. Uses the refined prompt from Phase 1 calibration
4. Generates detailed structured reports in `reviews/{entry_id}.json` (same format as Phase 1)
5. Each issue includes:
   - Field location (headword, examples[N].japanese, notes)
   - The specific text in question
   - What the model thinks is wrong
   - Suggested correction
   - Confidence level

#### Cost Control
- Add `--budget AMOUNT` flag that stops processing when estimated cost exceeds the amount
- Log cost per entry to help estimate full-dictionary costs
- Report estimated total cost for screening the full dictionary

```markdown
# Polish Cross-Model Review Results

Process multi-model review reports and apply corrections where appropriate. This is a **semantic task** — Claude evaluates each suggestion from external models and applies or rejects with reasoning.

## Task Focus

Read review reports generated by `build/review_runner.py`. For each flagged entry:
1. Read the review report
2. Read the actual entry
3. For each flagged issue:
   - Evaluate the suggestion using your knowledge of Japanese
   - If you AGREE the issue is real: fix it
   - If you DISAGREE: note your reasoning in the review log
   - If UNCERTAIN: flag for curator review

## Starting Point

```bash
cat polishing/tasks/cross-model-review/progress.txt
```

Process review files in `reviews/` that have flagged issues.

## Workflow

1. **Read the progress file** to find the next review to process
2. **Load the review report** from `reviews/{entry_id}.json`
3. **Load the actual entry** from `entries/{range}/{entry_id}_{romaji}.json`
4. **For each flagged issue**:
   - Read the concern and suggested correction
   - Evaluate against the actual entry context
   - Decision: APPLY, REJECT, or FLAG
   - If APPLY: fix the entry, update modified timestamp
   - If REJECT: log reasoning
   - If FLAG: add to `reviews/needs_curator.txt`
5. **After processing**: Update review file with resolution status
6. **Batch commits every ~25 entries**
7. **Session logging** to `polishing/sessions/cross_model_review_{date}_{nnn}.md`

## Important Notes

- Models disagree sometimes. When GPT-4.1 and Gemini disagree, use your own judgment.
- When all models agree on an issue, it's very likely real — apply the fix.
- When only one model flags something at low confidence, it's often a false positive.
- NEVER apply a correction you aren't confident about. When in doubt, flag for curator.
- Update the modified timestamp on any entry you change.
- Do NOT add inline word links (⟦...⟧) in this task.

## Session End

When finishing:
1. Update progress file
2. Write session log with:
   - Reviews processed
   - Corrections applied (with details)
   - Suggestions rejected (with reasoning)
   - Items flagged for curator
3. Run `make build`
4. Commit and push

### Part D: CI Integration (Phase 3)

Modify `.github/workflows/validate.yml` to add a post-merge review queuing step:

1. After successful validation on main branch:
   - Identify entry files changed in the merge commit
   - Write changed entry IDs to `reviews/queue.txt` (append, don't overwrite)
   - This creates a queue of entries needing review

2. Alternatively, create a separate workflow `.github/workflows/review-queue.yml`:
   ```yaml
   name: Queue Reviews
   on:
     push:
       branches: [main]
       paths: ['entries/**/*.json']
   jobs:
     queue:
       runs-on: ubuntu-latest
       steps:
         - uses: actions/checkout@v4
         - name: Find changed entries
           run: |
             git diff --name-only HEAD~1 HEAD -- 'entries/**/*.json' >> reviews/queue.txt
             sort -u reviews/queue.txt -o reviews/queue.txt
         - name: Commit queue update
           run: |
             git config user.name "github-actions"
             git config user.email "actions@github.com"
             git add reviews/queue.txt
             git diff --staged --quiet || git commit -m "Queue entries for multi-model review"
             git push
   ```

## Correction note (written after PR #3240 merged)

The furigana-screening half of this run was reported wrongly in PR #3240, and the sections above
have been rewritten. What happened, so the next run does not repeat it:

The screening pass was launched in the background and was still running when the analysis was
done — but `reviews/screening/` already held results for 13900–14399 from **2026-07-13/14/15**,
and the script overwrites those files in place without any run marker. Counting flagged files by
ID therefore looked like a completed 500-entry pass at an 8.4% flag rate. In reality only 222 of
those files were this run's; the other 278 were three-week-old leftovers.

The consequence was not just a wrong count. The July results predate the `trim_context()` fix,
so they are full of the "reading is cut off" false-positive family that the fix was written to
eliminate. Reading them as current output led to the conclusion that the fix had failed and that
`google/gemini-2.5-flash` was ignoring an explicit instruction. **The opposite is true**: that
family is entirely absent from this run's 222 fresh results. The fix worked.

The entry-level work in this run is unaffected. The accuracy-review analysis filtered on file
modification time and was sound, so all 9 applied corrections, the 48 rejections, and the §4
self-check stand as recorded.

What was corrected: this log; the `[tooling]` observation in `polishing/observations.md`; the
OpenRouter ledger (screening was booked at $0.20 for an assumed 500 entries, corrected by
-$0.11 to $0.09 for the 222 actually screened); and a retraction line in `reviews/decisions.jsonl`.

**Two artifacts still carry the wrong numbers and need the curator**, because both are
append-only by design and cannot be corrected in place — see `reviews/needs_curator.txt`:

### 2. Corpus swept to zero

All 291 links repaired across 159 entries; `modified` refreshed on each. 289 re-targeted,
2 set to `noentry`.

Verification unit was the **mapping**, not the entry: 291 occurrences reduce to 143 distinct
`(dead_id, baseform)` pairs, one of which (`00347_de` → `00502_de`) covers 47 links across 18
entries. Every one of the 143 mappings was adjudicated individually; occurrences were
spot-checked in situ.

- **111 single-candidate mappings** — target headword or reading equals the link's baseform, so
  the substitution is correct by construction (`取る`：`01286_toru`→`00565_toru`;
  `ある`：`00104_aru`→`00006_aru`; `批判`：`03580_hiban`→`03580_hihan`, a romaji typo).
- **32 ambiguous mappings** — all resolved and all context-checked. The deterministic rule
  *prefer the candidate whose headword equals the baseform character-for-character* picks the
  particle over its homographs every time (`も` over 藻/喪, `から` over 殻/空, `こと` over 琴/古都,
  `と` over 戸). Kanji-surface cases resolve by their own furigana (`{今日|きょう}`→`00496_kyou`;
  `{後|あと}`→`09580_ato`; `{日本|にほん}`→`03876_nihon`). Bivalent cases read in context: all six
  `いる` links are `〜ている` auxiliaries (→`00495_iru`), both `やすい` are `使いやすい`/`持ちやすい`
  (→`18367_yasui`, the suffix, not 安い), `もの` is a physical product (→`02259_mono`).
- **1 false resolution caught, and it is the finding worth keeping**: `ば` resolved to exactly one
  candidate, `03699_ba` 場 "place" — a reading homophone of the conditional particle, not the
  word. Applying the lookup's confident single answer would have turned a visibly-dead link into
  an invisibly-wrong working one. The risk class is narrow and screenable in advance — a *kana*
  baseform matching a *kanji*-headword entry, 3 of 111 mappings; the other two
  (`いっぱい`→一杯, `たち`→達) were verified correct.
- **2 links → `noentry`** (no entry exists to point at), both queued as candidates:
  `逆転する` (C22619, from 05510) and conditional `ば` (C22620, from 05595).

`python3 build/check_link_targets.py --summary` → 0 links, 0 entries, 0 dead IDs.

### 3. Inflow gate shipped — and the six-cycle diagnosis was wrong about the cause

Tooling 11 concluded across six cycles that `validate.py` has no link-target check. It has one:
`check_word_links()` has always resolved targets, and a full `make validate` was reporting
**308 word-link warnings** (291 dead + 17 malformed) the whole time. The real hole:

> `validate_single_entry()` — behind **both** `--entry` and `--id` — never called
> `check_word_links` at all. Neither did `validate_changed_only()` nor `validate_range()`.
> The check ran only in the full-corpus path a polish session never invokes, and the pre-commit
> hook (`validate.py --entry`) was blind for the same reason.

That is why three separate sessions wrote ad-hoc scanners re-implementing code in the file they
were running. Changes to `build/validate.py`:

- `check_word_links()` now returns `(errors, warnings)`; dead targets are **errors** (were
  warnings), so they fail `make validate` and CI. The 17 malformed-format links
  (`⟦surface→noentry⟧`, missing `：`) stay warnings — a separate family, untouched, so CI stays green.
- New `word_link_errors` field on `ValidationResult`, reported with a pointer to
  `check_link_targets.py --by-target`, and added to the exit-1 condition.
- New `load_all_entry_ids()` helper; `check_word_links` wired into `--entry`/`--id`,
  `--changed-only`, and `--range`, each checking against the **whole dictionary's** ID set.
- No baseline/ratchet needed: the corpus is at 0, so the check is absolute — stronger than the
  ratchet the item asked for, and only possible because sweep and gate shipped together.

Verified by injecting a synthetic dead link (`99999_bogus`) into 05595 and confirming exit 1 in
full, `--id`, and `--range` modes, then confirming exit 0 / 30,031-of-30,031 valid after removal.
`--changed-only` passes 159/159. **`build/tests/` could not be run — no `pytest` in this image
(wiki Tooling 42)**, so the four-mode injection test is the whole verification.

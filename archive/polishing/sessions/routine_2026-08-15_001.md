## Reviewer defect found: the `tags` dimension is inverted

Every one of the 80 tag-dimension flags was a confabulation. The pattern is exact
and repeated across all 20 sampled entries: the model invents a finer-grained tag
the entry does **not** carry, then "suggests" the tag the entry **already has**.

| Entry | Model says tag is invalid | Model suggests | Entry's actual tag |
|---|---|---|---|
| 10778 | `feeling-emotion` | `emotion` | `emotion` |
| 10782 | `person-reference` | `person` | `person` |
| 10785 | `quality-condition` | `descriptive` | `descriptive` |
| 10786 | `food-seafood`, `animal-shellfish` | `food`, `animal-general` | `food`, `animal-general` |
| 10796 | `abstract-concept`, `body-organ` | `abstract`, `body-internal` | `abstract`, `body-internal` |
| 10799 | `furniture-household`, `abstract-function` | `furniture`, `abstract` | `furniture`, `abstract` |

Meanwhile the reviewer flagged **none** of the 22 entries in the range that
genuinely carry off-vocabulary tags. Precision 0%, recall 0%.

`entry_payload()` in `build/review_accuracy.py` does send the real tags (as
`semantic_tags`), so this is model behaviour under the current prompt, not a
payload bug. Suggested fix: state in the prompt that `semantic_tags` is the
complete current tag list and that a tag may only be flagged if it appears
verbatim in that array.

**This matters for the prompt itself.** routine2.md §A step 4 says a flag that a
tag is not in the valid list "is correct by definition: APPLY it by migrating to
the suggested tag." Against this failure mode that rule is unsafe — the flagged
tag does not exist in the entry, and the suggestion equals the current value, so
applying would have logged 80 phantom fixes as real and inflated the tags
dimension's measured precision to 100%. A guard is needed: verify the flagged tag
literally appears in `metadata.tags.semantic` before applying.

## Observations logged

- `[pattern]` Katakana loanwords wrapped in furigana braces with a hiragana
  "reading" (`{レポート|れぽーと}`, `{ルール|るーる}`, `{タクシー|たくしー}`).
  Katakana takes no ruby, so these print a redundant hiragana gloss above the
  word. **50 entry files affected**; `grep -rlo '{[ァ-ヴー]\+|' entries/` finds
  them. Fixed by hand in 01087 only — a dictionary-wide pass belongs to
  `systemic-fix` mode.
- `[tooling]` `build/check_furigana_format.py` already detects these, but buries
  them among 374 undifferentiated `pure-kana` warnings and offers no suggested
  fix, so they never surface as actionable. Proposed a `katakana-ruby`
  subpattern: surface all-katakana, reading = that surface in hiragana,
  suggestion = drop the wrapper. That subclass is mechanically safe, which would
  turn a large unactionable warning pile into a small clean batch.

Also noticed but not logged as a separate item: `part_of_speech` is free text and
has drifted badly (18,744 `noun`, plus `noun, suru verb` / `noun, suru-verb` /
`noun, verb-suru` / `noun / suru verb` as four spellings of one thing, and 19
entries using hiragana `な-adjective`). It is a display field, so nothing is
broken, but it is a candidate for a normalization pass.

## Tooling note

Wrote a throwaway link-proposal script (scratchpad, not committed) that does
greedy longest-match against `build/word_id_lookup.json` and prints OK /
AMBIGUOUS / no-match per token. It made the frontier linking practical, and its
false positives are instructive: it happily proposed いた→板 "plank" for the
`〜ていた` ending, り→利 "profit" inside 走り続ける, and てか→06284 inside
してから. Greedy matching cannot be trusted to write links unsupervised, but as
a lookup aid that flags what needs judgment it saves a great deal of time.
Worth building properly (as `build/propose_links.py`) if a future run wants to
attack the unlinked backlog at scale.

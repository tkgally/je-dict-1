# Deterministic vs. Semantic Editorial Tasks

**Last updated**: 2026-08-02

## Overview

The je-dict-1 project involves dozens of editorial tasks that range from purely mechanical operations (schema validation, conjugation generation, index rebuilding) to deeply semantic work (writing usage notes, choosing cross-references, verifying furigana readings in context). Understanding which tasks fall where on this spectrum — and why the boundary matters — is essential for project efficiency, quality control, and future automation planning.

This page documents the full taxonomy, analyzes the boundary in detail, and records the project's hard-won lessons about when programmatic approaches are appropriate and when they are not.

## Historical context: why this matters

Early in the project, Claude (the LLM doing most editorial work) sometimes attempted to accelerate dictionary-building tasks by writing Python scripts to mass-produce entries or automate editorial decisions. This was a natural instinct — an LLM that can write code sees a batch of 30 similar tasks and thinks "I could write a loop." But the results were consistently poor:

- **Mass-produced entries were shallow.** A script that generates entries from a template produces entries that all sound alike. Each Japanese word has its own collocational preferences, register characteristics, learner pitfalls, and cultural associations. A template cannot capture these.
- **Automated editorial judgments were unreliable.** A script that assigns semantic labels based on keyword matching or that adds cross-references based on shared readings produces many false positives and misses the cases that actually matter.
- **The errors were hard to catch.** When entries are written one at a time, a bad entry stands out during review. When 30 entries are generated by a script, systematic errors propagate silently across all of them.

This experience led to the explicit warnings now found throughout the project's prompts and skills — phrases like "DO NOT use Python scripts or automation to mass-produce entries" and "this is a semantic task that cannot be automated." These warnings exist because they address a real, observed failure mode, not a hypothetical concern.

## The two-layer architecture

The project has settled on a clear separation between two layers:

### Deterministic layer (Python scripts in `build/`)

These scripts handle tasks that require no semantic judgment. Their inputs are entry files and configuration; their outputs are HTML files, index files, validation reports, and conjugation tables. They are:

- **Reproducible**: Same input always produces same output
- **Verifiable**: Correctness can be checked mechanically
- **Safe to run repeatedly**: No risk of degrading content quality
- **Fast**: Process thousands of entries in seconds

### Semantic layer (LLM-driven prompts and skills)

These tasks require understanding Japanese language, learner needs, and editorial judgment. They are:

- **Non-deterministic**: Different runs may produce different (but equally valid) results
- **Context-dependent**: The right answer depends on meaning, usage, and audience
- **Quality-variable**: Output quality depends on the care taken per item
- **Slow**: Each item requires individual attention

The boundary between these layers is one of the project's most important architectural decisions.

## Complete task taxonomy

### Fully deterministic tasks (Python scripts)

These tasks involve no semantic judgment whatsoever. They are implemented as Python scripts in `build/` and run as part of the standard build pipeline.

| Task | Script | What it does |
|------|--------|-------------|
| Schema validation | `validate.py` | Checks entry JSON against schema — structure, required fields, format |
| Tag validation | `validate_tags.py` | Verifies tag values against fixed enumerations |
| Verb conjugation | `add_conjugations.py` | Generates all conjugated forms from verb class + stem |
| I-adjective conjugation | `add_adjective_conjugations.py` | Generates conjugated forms from stem (including irregular いい) |
| Index updates | `update_indexes.py` | Syncs `entries_index.json` with filesystem, removes created candidates |
| Static site build | `build_flat.py` | Renders HTML from entry JSON — deterministic templating |
| Search index | `search_index_builder.py` | Builds JavaScript search indexes from entry data |
| Kanji extraction | `extract_kanji_from_entries.py` | Scans headwords for kanji characters |
| Kanji index update | `update_kanji_index.py` | Rebuilds kanji-to-entry mappings |
| Word lookup table | `generate_word_lookup.py` | Builds word→entry_id map for inline links |
| Missing furigana scan | `find_missing_furigana.py` | Pattern-matches for kanji without `{漢字\|かんじ}` markup |
| Duplicate detection | `check_duplicate.py` | Exact-match comparison of headword + reading |
| Merge candidate detection | `find_merge_candidates.py` | Finds entries sharing readings, missing cross-refs |
| Candidate management | `manage_candidates.py` | Add/remove/sync candidate word list |
| Candidate cleanup | `cleanup_candidates.py` | Removes internal duplicates from candidate list |
| Link resolution | `resolve_links.py` | Converts unresolved inline links to resolved ones via lookup table |
| Reference hardening | `harden_references.py` | Adds missing target IDs to cross-references |
| Sitemap generation | `build_sitemap.py` | XML sitemap from entry metadata |
| Report generation | `report.py` | Statistics dashboard — counts, gaps, distributions |
| ID allocation | `get_next_id.py` | Returns next available 5-digit ID |
| Path calculation | `get_entry_path.py` | Computes correct filesystem path for an entry |
| Timestamp | `get_timestamp.py` | Returns current UTC timestamp |

**Key characteristic**: Every one of these scripts operates on *form*, never on *meaning*. `validate.py` checks that an entry has a `notes` field, not that the notes are helpful. `add_conjugations.py` applies phonological rules to a verb stem, not semantic judgment about which conjugations are most useful. `find_missing_furigana.py` detects kanji characters without markup, not whether the reading is correct.

### Fully semantic tasks (LLM editorial work)

These tasks cannot be reduced to rules or patterns. They require understanding what words mean, how they are used, and what learners need to know.

| Task | Prompt/Skill | Why it requires semantic judgment |
|------|-------------|----------------------------------|
| Entry creation | `newentries.md`, entry skills | Every word has unique collocations, register, learner difficulties |
| Usage notes writing | `expand-short-notes.md`, `vocabulary-notes` skill | Must explain meaning, patterns, and pitfalls specific to each word |
| Example sentence writing | Part of entry creation | Sentences must be natural, demonstrate the target word, and use appropriate vocabulary |
| Cross-reference selection | `add_cross-references.md` | Must understand semantic relationships between words |
| Furigana reading assignment | `polish_furigana_completeness.md` | Correct reading depends on compound word rules, context, irregular readings |
| Furigana correctness verification | `polish_furigana_correctness.md` | Must know if a reading is right for this kanji in this context |
| Semantic label assignment | `polish_semantic_labels.md` | Must understand what the word means to categorize it |
| Inline link placement | `polish_add_inline_links.md` | Must identify word boundaries, resolve homographs, verify meaning in context |
| Example sentence evaluation | `polish_example_sentences.md` | Must assess naturalness, vocabulary appropriateness, sense coverage |
| Candidate word discovery | `newcandidates.md`, `find-candidates` skill | Requires understanding what vocabulary gaps exist |
| Candidate evaluation | `clean_up_candidates_list.md` | Must judge whether a candidate is a real word worth including |
| Corpus harvesting | `corpus_harvesting.md` | Must evaluate exclusion criteria (proper nouns, archaic, slang) |

**Key characteristic**: These tasks all involve judgments about *meaning* — what a word means, how it is used, what learners need to know about it, and how it relates to other words.

### Hybrid tasks (deterministic detection + semantic judgment)

These are the most interesting category. A script identifies candidates mechanically, but a human or LLM must make the final decision.

| Task | Detection method | Semantic judgment required |
|------|-----------------|--------------------------|
| Entry consolidation | `find_merge_candidates.py` finds entries with shared readings | Must determine if entries are true duplicates, spelling variants, or unrelated homophones |
| Duplicate ID resolution | Script detects shared 5-digit IDs | Must decide which entry keeps the ID based on content and history |
| Candidate deduplication | Script finds candidates matching existing entries by reading | Must evaluate whether the candidate is truly the same word or a different word with the same reading |
| Cross-reference gap detection | Script finds entry pairs that lack reciprocal references | Must evaluate whether the detected gap represents a genuine missing link or a false positive |

The consolidation task is the clearest example of the hybrid pattern. The prompt states it directly: "This is a **semantic task** — the detection script finds candidates deterministically, but you must judge each case using your knowledge of Japanese." The script `find_merge_candidates.py` flags that entries 01234 and 05678 share the reading "こうしょう," but only a semantic agent can determine whether these are 交渉 (negotiation) and 公称 (nominal) — two completely different words that happen to be homophones — or whether they are genuinely the same word written in different ways.

## Why certain tasks resist automation

### The furigana problem

Furigana (adding readings to kanji) appears at first glance to be automatable — surely a dictionary of kanji readings could handle this? But the task is deeply context-dependent:

- **Compound readings**: 今日 is usually きょう, but in the phrase 今日的 it is こんにち. 大人 is おとな in most contexts but だいにん in Buddhist terminology.
- **Rendaku** (sequential voicing): 花 is はな alone but ばな in 花火 (はなび). Rules exist but have many exceptions.
- **Name readings**: 山田 could be やまだ or やまた or several other readings.
- **On/kun selection**: 山 is やま in native words but さん/ざん in Sino-Japanese compounds. The choice depends on the word, not just the kanji.
- **Stylistic readings**: Some words have alternate readings used in literary or formal contexts (e.g., 今朝 as けさ vs. こんちょう).

A lookup table could handle the common cases, but the uncommon cases — which are exactly the ones learners most need help with — require contextual understanding. The project tried mechanical furigana detection (`find_missing_furigana.py`) for finding *gaps*, which works well, but the actual *assignment* of correct readings is a semantic task.

### The cross-reference problem

Cross-references seem automatable: find words with related meanings and link them. But:

- **Not all related words deserve cross-references.** 犬 (dog) and 猫 (cat) are related, but linking every animal to every other animal creates noise. The judgment of "is this relationship *useful to a learner*?" is inherently semantic.
- **Relationship types matter.** A transitive/intransitive pair (上げる/上がる) is different from a synonym pair (美しい/きれい) is different from an antonym pair (大きい/小さい). Correct type assignment requires understanding the relationship.
- **Directionality is asymmetric.** A common word like 行く may not need a prominent link to a rare word like 赴く, but the reverse link is essential for the learner encountering the rare word.

### The example sentence problem

Example sentences are perhaps the clearest case where automation fails completely. A good example sentence must simultaneously:

1. **Demonstrate the target word naturally** — not a forced context
2. **Use vocabulary at the right tier** — basic/core words only for basic tier entries
3. **Illustrate a specific sense** — not ambiguous between senses
4. **Progress in difficulty** — from simple to complex across the set
5. **Cover different usage contexts** — not all the same pattern
6. **Sound like something a native speaker would actually say**

A template or pattern-based generator cannot satisfy all six requirements simultaneously. Each sentence requires a small creative act grounded in linguistic knowledge.

### The semantic label problem

Semantic labels (tags like "food," "emotion," "body") seem like they could be assigned by keyword matching — if the definition mentions "food," tag it "food." But:

- **Words have multiple semantic domains.** 酒 (sake/alcohol) is both "food-drink" and "culture." Which is primary?
- **Template artifacts persist.** Early entries sometimes received default tags that don't match the word's meaning. Detecting these requires understanding the word, not just reading the tag.
- **Granularity judgments are subjective.** Is 走る (to run) best tagged as "movement," "sports," or "daily-life"? The answer depends on how the word is most commonly used and what would be most helpful for learners.

## The "trend toward the mean" advantage for semantic tasks

As discussed in [LLMs as Lexicographic Corpus Replacements](llms-replacing-corpora.md), the LLM's tendency to produce average, consensus-level output — often criticized in creative contexts — is an advantage for lexicographic work. Dictionary entries *should* reflect mainstream usage. When Claude writes that 電話を切る means "to hang up the phone" and generates examples showing this in common contexts, the "trend toward the mean" is producing exactly the right thing.

This is why the LLM-driven approach works despite being non-deterministic. The variation between runs is variation within the space of *reasonable dictionary content*, not random noise. Two different sessions might produce slightly different example sentences for the same word, but both sets would be natural, appropriate, and useful.

## Spectrum, not binary

The deterministic/semantic distinction is a spectrum, not a sharp line. Some tasks that are currently treated as fully semantic could be partially automated with the right tooling:

### Automatable components within semantic tasks

| Semantic task | Component that could be automated | Component that cannot |
|--------------|----------------------------------|----------------------|
| Furigana completeness | Detection of missing furigana (already done) | Correct reading assignment |
| Example sentences | Counting examples, measuring length | Writing new examples, evaluating naturalness |
| Semantic labels | Detecting obviously wrong labels (e.g., "food" on an emotion word) | Assigning correct labels to ambiguous cases |
| Cross-references | Detecting missing reciprocal links (already done) | Deciding which new links to add |
| Inline links | Looking up entry IDs for known words (already done via lookup table) | Identifying word boundaries, resolving homographs |
| Entry consolidation | Detecting shared-reading candidates (already done) | Judging whether to merge or keep separate |

The project has already extracted the automatable components from most hybrid tasks — the `find_merge_candidates.py`, `find_missing_furigana.py`, `resolve_links.py`, and `check_duplicate.py` scripts are all examples of this pattern. What remains in the semantic layer is genuinely irreducible.

### Potential future automation

Some tasks that are currently fully semantic could become partially automatable with better tooling:

- **Furigana assignment**: A comprehensive kanji reading database cross-referenced with compound word dictionaries could handle ~90% of cases, leaving only irregular and context-dependent readings for manual review.
- **Vocabulary tier checking in examples**: A word-to-tier lookup could flag examples that use general-tier words in basic-tier entries, reducing the manual review burden.
- **Cross-reference suggestions**: An embedding-based similarity search could suggest candidate cross-references, with the LLM reviewing suggestions rather than generating them from scratch.

But even in these cases, the automation would produce *candidates* for review, not *final decisions*. The semantic layer remains as the ultimate quality gate.

## Design principles

The project's experience has crystallized several principles:

### 1. Automate detection, not decision

Scripts should find problems and candidates. Humans and LLMs should decide what to do about them. This is the pattern of `find_merge_candidates.py` (finds candidates) + `consolidate_entries.md` (decides on merges), and it works well.

### 2. Never automate content generation

Entry text — definitions, examples, notes, usage explanations — must always be written with semantic understanding. Even when creating 30 entries in a session, each one is written individually. The "individually by hand" instruction in the entry guidelines is the project's most important quality control.

### 3. Deterministic scripts are trust-once, run-forever

Once a build script is verified correct, it can be run thousands of times without degrading quality. This is why the project invests in robust validation (`validate.py`, `validate_tags.py`) and build scripts — they form a reliable foundation.

### 4. Semantic tasks require fresh attention each time

Unlike scripts, semantic tasks cannot be assumed correct just because they worked last time. Each entry, each cross-reference, each furigana reading is a new judgment that could go wrong. This is why polishing tasks process entries one at a time rather than in bulk.

### 5. The hybrid pattern is the sweet spot

The most effective workflow is: **deterministic script identifies candidates → semantic agent reviews and acts**. This combines the speed and reliability of automation with the judgment of semantic understanding. Almost every polishing task follows this pattern, even if the "detection" step is simply "read the next entry in sequence."

## Implications for future development

### Multi-model review

The [Multi-Model Proofreading](../ideas/multi-model-proofreading.md) proposal would use multiple LLMs to review entries. This is an example of using *more* semantic reasoning, not less — the insight being that different models may catch different errors. The deterministic scripts remain the same; the semantic layer gets deeper.

### Parallel agents

The [Parallel Agent Architecture](../ideas/parallel-agent-architecture.md) would run multiple LLM agents simultaneously. The safety concern is ensuring that parallel semantic agents don't interfere with each other. The deterministic layer (validation, indexing, building) naturally serializes through the build pipeline, providing a consistency checkpoint.

### New automation opportunities

As the dictionary grows, new deterministic scripts will be needed:
- **Consistency checkers** that flag entries where similar words have inconsistent note structures
- **Coverage analyzers** that identify semantic domains with thin coverage
- **Quality scorers** that rank entries by a rubric for polishing prioritization

These are all detection tools — they expand the deterministic layer's ability to find problems without encroaching on the semantic layer's role in fixing them.

## Measured 2026: the same distinction, applied to what the project pays a model for

The 2026 Routine spends real money on cross-model review, and it buys four dimensions —
`furigana`, `gloss`, `translation`, `tags`. Two years of this page's argument predicts they should
not be equally worth buying, and by mid-2026 there is enough evidence to sort them. **The test is
not "is this task semantic?" but "is the *detection* step semantic?"** — because that is the half
being paid for.

**`tags` — detection is deterministic; only the destination is semantic.** Five consecutive
review blocks found that a free set-difference against `VALID_SEMANTIC` finds nearly everything
the paid reviewer flags (110 of 118 in one block, 38 of 54 in another). A tag that is not in the
list is wrong *by definition*; no judgment is involved in noticing it. What genuinely needs a
model is choosing where it should go instead — and even that splits, because for *forced* renames
(`medicine`→`health`) the destination follows from the tag name alone, and for context-dependent
labels the safe move is to drop rather than migrate. So the model is being paid for detection it
cannot improve on. This is the hybrid pattern with the split drawn in the wrong place; the
correction is [Tooling 46](../ideas/tooling-backlog.md#46-pre-scan-off-vocabulary-tags-deterministically-and-feed-the-list-to-the-accuracy-reviewer)
— scan for free, ask the model only for destinations.

**`translation` — detection is irreducibly semantic.** A single 2026-08-02 review block produced
two defects that no linter can express: a romaji Japanese word left inside an English translation
("The word 'suchuwaadesu' used to be commonly used", 23893), and a translation that *contradicts*
its Japanese sentence (「{山|さん}」は{字音|じおん}だ rendered as "'San' is the on-reading", where
the Japanese asserts the character *is* an on-reading, 23894). The first is arguably reachable by
a heuristic — an improbable letter sequence in an English field — but the second is a
truth-conditional comparison between two languages, which is the definition of the semantic layer.
This dimension is what the money is for.

**`furigana` — detection was semantic in principle and worthless in practice.** The screening pass
has now run six consecutive measured windows at **zero** precision (0 of ~64 flags applied). Its
historical true-positive classes turn out to be exactly the ones a cheap lint can express —
non-hiragana readings, orphan kana, unwrapped headwords — while its false positives cluster in
families (rendaku in compounds, okurigana splits, readings the entry itself discusses) that are
properties of Japanese orthography, not of the entry. It is the counterexample to a naive reading
of this page: *semantic* does not imply *worth a model*, because a model with no reliable evidence
produces confident noise rather than judgment. Full analysis:
[Tooling 24](../ideas/tooling-backlog.md#24-non-hiragana-reading-lint-cheap-replacement-for-the-furigana-screeners-true-positive-class).

The refinement this adds to **design principle 1 ("automate detection, not decision")**: the
principle assumes detection is the automatable half. That holds only when the defect has a
mechanical signature. Where it does — off-vocabulary tags, dead link targets, bare-kanji headwords
— buying detection from a model is pure waste, and the free scan should feed the model rather than
compete with it. Where it does not — cross-language truth conditions, whether a note explains the
word or merely restates it — detection *is* the product. Sorting the review budget by that
question, rather than by dimension name, is what the [quality metrics](quality-metrics.md)
time series has made possible.
